## 0. 조사 제약과 전제

작성에 앞서 밝혀 둘 사항이 있다. 참고 사이트 `www.withonesolution.com` 은 현재 작업 환경의 네트워크 정책에 의해 직접 열람이 차단되어, 페이지를 눈으로 확인하지 못했다. 대신 검색 엔진에 색인된 정보로 다음 사실을 확인했다.

| 확인 항목 | 내용 |
| --- | --- |
| URL 구조 | `/sub/sub04_01.php?mNum=4&sNum=1&boardid=notice&mode=view&idx=35` |
| 구현 방식 | PHP 기반, 메뉴 번호(mNum/sNum) 파라미터로 페이지를 분기하는 전형적 국내 중소기업형 사이트 |
| 게시판 규모 | 목록 페이지에 `offset=160` 이 존재, 게시물 160건 이상 누적 |
| 게시물 성격 | "시립청소년성문화센터 동작사무소" 등 공공기관명이 게시물 제목으로 노출 |
| 브랜드 연관 | 동일 계열로 추정되는 `withonesoft.co.kr` 이 대량메일, UMS 통합메시지, PUSH, 동영상 스트리밍, Live 통합방송, 멀티미디어 아카이브, 온라인 설문(e-Survey), 웹·모바일 채팅, 문서변환/뷰어, 보안 솔루션을 제공 |

이 단서를 종합하면 벤치마크 사이트는 **공공기관과 기업을 주 고객으로 하는 소프트웨어 솔루션 기업의 회사 소개형 웹사이트**이며, 제품 카탈로그와 납품·구축 실적 게시판을 핵심 콘텐츠로 삼는 구조다. 본 기획서는 이 성격을 전제로 작성했다.

전제가 실제와 다를 경우 조정이 필요한 범위는 2장 서비스 정의와 5장 정보구조에 한정되며, 6장 이후의 기능·디자인·기술·일정 계획은 그대로 유효하다.

## 1. 프로젝트 개요

### 1.1 목적

현행 PHP 게시판형 사이트가 가진 한계를 걷어내고, 공공 조달 담당자와 기업 IT 담당자가 **제품을 이해하고 문의까지 도달하는 경로**를 최단으로 만드는 것이 이 프로젝트의 목적이다.

벤치마크 사이트의 구조적 한계는 세 가지로 요약된다.

- **검색 유입이 막혀 있다.** 쿼리스트링 기반 URL은 검색 엔진이 콘텐츠를 구분하기 어렵고, 실제로 색인된 페이지가 극소수다.
- **실적이 자산으로 쓰이지 않는다.** 160건 넘는 납품 이력이 단순 게시판 목록으로만 존재해, 산업별·솔루션별로 탐색할 수 없다.
- **모바일 대응과 접근성 기준을 충족하지 못한다.** 공공기관 대상 사업에서 웹 접근성은 사실상 필수 요건이다.

### 1.2 범위

| 구분 | 포함 | 제외 |
| --- | --- | --- |
| 사이트 | 국문 기업 웹사이트 전체, 관리자 CMS | 영문 사이트(2차), 고객 포털·로그인 영역 |
| 콘텐츠 | 제품 상세 8종, 회사 소개, 실적 DB 이관 | 신규 제품 브로슈어 촬영·영상 제작 |
| 기술 | 프론트엔드·백엔드·배포·SEO·접근성 | 사내 ERP 연동, 결제 모듈 |

### 1.3 성공 지표

| 지표 | 현재(추정) | 목표(오픈 6개월 후) |
| --- | --- | --- |
| 월간 순 방문자 | 500명 이하 | 3,000명 |
| 검색 색인 페이지 수 | 10건 미만 | 150건 이상 |
| 월간 문의 제출 건수 | 5건 이하 | 30건 |
| 문의 전환율 | 1% 미만 | 2.5% |
| 모바일 트래픽 비중 | 20% 미만 | 40% |
| 접근성 심사 | 미인증 | 웹 접근성 품질인증 획득 |

## 2. 타깃 사용자

### 2.1 1차 타깃: 공공기관 사업 담당자

지자체, 공사, 교육기관에서 정보화 사업을 발주하는 실무자다. 나라장터 공고 전에 시장 조사를 하며, **비슷한 기관에 납품한 이력이 있는지**를 가장 먼저 확인한다. 제안요청서 작성을 위해 기능 명세와 규격을 문서로 받고 싶어 한다.

필요한 것: 동종 기관 구축 사례, 제품 규격서 PDF, 조달 등록 여부, 담당자 직통 연락처.

### 2.2 2차 타깃: 기업 IT·정보보안 담당자

사내 메시징이나 영상 시스템 도입을 검토한다. 경쟁 제품과 기능을 비교하고, 도입 후 유지보수 체계를 따진다.

필요한 것: 기능 비교표, 연동 규격과 API 문서, 도입 절차, 기술 지원 범위.

### 2.3 3차 타깃: 협력사·구직자

파트너 제휴를 타진하거나 채용 공고를 확인한다. 회사 규모와 안정성을 판단할 근거를 찾는다.

필요한 것: 회사 연혁, 인증·특허 현황, 재무 신뢰 신호, 채용 공고.

### 4.2 메뉴 설계 원칙

상단 글로벌 내비게이션은 6개를 넘기지 않는다. 솔루션 메뉴는 마우스를 올리면 8개 제품을 2열 그리드와 한 줄 설명으로 펼치는 메가 메뉴를 쓴다. 모바일에서는 아코디언으로 전환한다.

우측 상단에는 상시 노출 CTA 버튼 하나를 둔다. 문구는 "도입 문의"로 고정한다.

## 5. 주요 화면 정의

### 5.1 메인 페이지

| 순서 | 섹션 | 구성 요소 | 목적 |
| --- | --- | --- | --- |
| 1 | 히어로 | 한 줄 가치 제안, 보조 설명, CTA 2개(도입 문의·솔루션 보기), 배경 비주얼 | 3초 안에 무엇을 하는 회사인지 전달 |
| 2 | 신뢰 지표 | 누적 구축 건수, 고객 기관 수, 업력, 인증 배지 | 규모와 안정성 즉시 증명 |
| 3 | 솔루션 그리드 | 8개 카드(아이콘·명칭·한 줄 설명·바로가기) | 제품 전반 조망 |
| 4 | 대표 구축사례 | 사례 3건 슬라이드(기관 로고·과제·결과 수치) | 실적을 서사로 전환 |
| 5 | 고객 로고 월 | 기관 로고 12~20개 그리드 | 사회적 증명 |
| 6 | 도입 절차 | 문의 → 상담 → 제안 → 구축 → 유지보수 5단계 | 진입 장벽 해소 |
| 7 | 소식 | 공지·자료실 최신 3건 | 운영 중인 회사임을 표시 |
| 8 | 하단 CTA | 문의 폼 축약형 또는 상담 예약 | 이탈 직전 전환 |

### 5.2 솔루션 상세 페이지 (템플릿 1종, 8회 사용)

페이지는 다음 순서를 따른다. 제품이 달라도 골격은 같게 유지해 제작과 유지보수 비용을 줄인다.

1. **헤더** — 제품명, 한 줄 정의, 자료 다운로드 버튼, 문의 버튼
2. **이런 고민이 있으신가요** — 고객이 겪는 문제 3가지
3. **핵심 기능** — 기능 카드 4~6개, 각 카드에 스크린샷 또는 다이어그램
4. **시스템 구성도** — 연동 구조 도식 1장
5. **도입 효과** — 정량 지표 3개 (처리량, 절감률, 응답 시간 등)
6. **적용 사례** — 해당 솔루션이 들어간 구축사례 자동 연결 3건
7. **규격 및 요구 환경** — 지원 OS, 브라우저, 연동 규격 표
8. **자주 묻는 질문** — 3~5문항
9. **문의 폼** — 제품명이 자동 입력된 상태로 노출

### 5.3 구축사례 목록

좌측 또는 상단에 필터 3종을 둔다. 산업(공공·교육·금융·의료·기업), 솔루션(8종), 연도. 필터 상태는 URL 쿼리에 반영해 공유와 색인이 가능하게 한다.

카드에는 기관명, 산업 태그, 적용 솔루션 태그, 연도, 한 줄 성과를 표시한다. 기관 로고 사용은 사전 동의를 받은 건에 한한다.

### 5.4 구축사례 상세

과제 → 해결 방안 → 적용 솔루션 → 결과 순으로 서술한다. 결과에는 가능한 한 수치를 넣는다. 하단에 동일 산업 사례 3건과 문의 CTA를 붙인다.

기관명 공개가 어려운 건은 "수도권 광역지자체 A" 형태로 익명 처리하되 산업과 규모는 남긴다.

### 5.5 문의하기

필수 입력은 5개로 제한한다. 기관·회사명, 담당자명, 연락처 또는 이메일, 문의 유형, 문의 내용. 선택 입력으로 관심 솔루션과 도입 예정 시기를 둔다.

개인정보 수집·이용 동의 체크박스는 필수이며, 동의 내용 전문을 접힌 상태로 함께 노출한다. 제출 후에는 접수 번호와 예상 회신 시간을 안내한다.

### 6.1 관리자 CMS 요구사항

운영 담당자가 개발자 도움 없이 콘텐츠를 다룰 수 있어야 한다. 최소 요건은 다음과 같다.

- 구축사례 등록 시 산업·솔루션·연도 태그를 선택식으로 지정
- 이미지 업로드 시 자동 리사이즈와 WebP 변환
- 공지·자료실 첨부파일 용량 제한과 확장자 화이트리스트
- 문의 내역 목록 조회, 처리 상태 변경, 엑셀 내려받기
- 2단계 인증 또는 관리자 IP 제한

## 7. 디자인 가이드

### 7.1 톤앤매너

공공 조달 담당자가 보는 화면이다. 화려함보다 **신뢰와 가독성**이 우선한다. 여백을 넉넉히 쓰고, 정보 밀도는 높이되 정렬을 엄격히 맞춘다. 스톡 이미지 남용은 피하고 실제 구성도와 스크린샷을 쓴다.

### 7.2 컬러

| 역할 | 용도 |
| --- | --- |
| Primary | 브랜드 딥 블루 계열, CTA와 강조 |
| Secondary | 시안 또는 틸 계열, 보조 강조와 그래프 |
| Neutral | 텍스트·배경 9단계 그레이 스케일 |
| Semantic | 성공·경고·오류 각 1색 |

본문 텍스트와 배경의 명도 대비는 4.5:1 이상, 큰 텍스트는 3:1 이상을 지킨다.

### 7.3 타이포그래피

본문은 Pretendard 또는 Noto Sans KR을 쓴다. 본문 16px, 행간 1.7을 기준으로 한다. 제목은 32/28/24/20px 4단계로 제한한다.

### 7.4 그리드와 컴포넌트

데스크톱 12칼럼, 최대 폭 1200px, 거터 24px. 모바일 4칼럼, 좌우 여백 16px.

공통 컴포넌트는 버튼 3종(주·보조·텍스트), 카드 3종(솔루션·사례·소식), 표, 아코디언, 탭, 배지, 페이지네이션, 폼 요소 일체, 토스트를 정의한다. 컴포넌트는 디자인 토큰으로 정의해 코드와 1:1 대응시킨다.

## 8. 기술 설계

### 8.1 권장 구성

| 영역 | 선택 | 근거 |
| --- | --- | --- |
| 프론트엔드 | Next.js (App Router) + TypeScript | 정적 생성으로 SEO 확보, 페이지 단위 증분 재생성 |
| 스타일 | Tailwind CSS + 디자인 토큰 | 컴포넌트 일관성, 유지보수 용이 |
| 콘텐츠 | 헤드리스 CMS(Strapi 자체 호스팅) 또는 DB 직결 관리자 | 공공 고객 특성상 데이터 국내 보관 필요 |
| 데이터베이스 | PostgreSQL | 사례 필터링 쿼리에 적합 |
| 호스팅 | 국내 클라우드(NCP·KT Cloud) 또는 AWS 서울 리전 | 공공 대상 사업의 데이터 소재지 요건 |
| 메일 발송 | 자사 메일 솔루션 연동 | 도그푸딩, 외부 비용 절감 |
| 분석 | Google Analytics 4 + 자체 이벤트 로깅 | 전환 추적 |

대안으로 운영 인력이 개발 리소스를 갖추기 어렵다면 WordPress + ACF 조합도 성립한다. 초기 구축은 빠르지만 보안 패치 부담과 플러그인 의존이 장기 비용으로 돌아온다는 점을 함께 고려해야 한다.

### 8.2 URL 정책

- 소문자 영문과 하이픈만 사용한다.
- 구 사이트 URL은 301 리다이렉트로 신규 경로에 매핑한다. 게시물 `idx` 기준 매핑표를 이관 시 작성한다.
- 필터는 쿼리스트링을 쓰되, 주요 조합은 정적 경로로도 노출한다.

### 8.3 성능 목표

| 지표 | 목표 |
| --- | --- |
| Largest Contentful Paint | 2.5초 이하 |
| Interaction to Next Paint | 200ms 이하 |
| Cumulative Layout Shift | 0.1 이하 |
| Lighthouse 성능 점수 | 모바일 85점 이상 |

이미지는 WebP 또는 AVIF로 제공하고, 화면 밖 이미지는 지연 로딩한다. 폰트는 서브셋 처리 후 `font-display: swap` 을 적용한다.

### 8.4 보안

- 전 구간 HTTPS, HSTS 적용
- 폼 제출에 CSRF 토큰과 서버 측 검증
- 파일 업로드 확장자 화이트리스트와 실행 권한 차단
- 관리자 영역 접근 IP 제한 또는 2단계 인증
- 개인정보 저장 항목 최소화, 문의 데이터 보관 기간 정책 수립(예: 3년)
- 정기 취약점 점검 연 1회

### 8.5 접근성

한국형 웹 콘텐츠 접근성 지침 2.2를 기준으로 설계한다. 핵심 점검 항목은 다음과 같다.

- 모든 이미지에 의미 있는 대체 텍스트
- 키보드만으로 전 기능 이용 가능, 포커스 표시 명확
- 동영상에 자막 제공
- 폼 요소에 레이블 연결과 오류 안내 텍스트
- 자동 재생·깜빡임 요소 배제
- 표에 제목과 요약, 머리글 셀 지정

오픈 전 전문 기관 심사를 거쳐 웹 접근성 품질인증 취득을 목표로 한다.

### 8.6 검색 엔진 최적화

페이지별 고유 title과 description을 작성한다. 조직 정보는 Organization, 제품은 Product, FAQ는 FAQPage 구조화 데이터를 넣는다. sitemap.xml 자동 생성과 robots.txt를 배치하고, 네이버 서치어드바이저와 구글 서치 콘솔에 등록한다.

공공 조달 담당자가 실제로 검색하는 표현을 중심으로 키워드를 잡는다. "기관명 + 솔루션명", "OO시스템 구축", "UMS 도입" 같은 조합이 여기 해당한다.
